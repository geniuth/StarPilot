# ID.4 공조(HVAC) 리버싱 — 진행 기록

목표: 원격 공조(주차 중 예열/예냉)를 콤마로 구동할 수 있는지 판정.
한국 사양은 We Connect(커넥티드 서비스) 미제공이라 차량 클라우드 경로가 없다.

## 1차 조사 결과 (2026-07, 기존 rlog 분석)

### 읽기: 공조 상태는 전부 보인다
`docs/id4_open_items.md`의 "외기온도(`Klima_Sensor_*`) 부재" 판정은 **오류**였다.
실제 주행 rlog에서 아래가 모두 수신된다.

| 메시지 | 버스 | 확인된 신호/값 |
|---|---|---|
| `Klima_11` (0x3B5) | 1 | `KL_AC_Schalter=1`(에어컨 ON), `KL_Anf_KL=42~43%`, `KL_Zustand=1` |
| `Klima_12` (0x668) | 0, 2 | `KL_Geblspng_Soll=4.6~5.0V`(송풍), `KL_SIH_Soll_li/re=0`(시트히터) |
| `Klima_Sensor_02` (0x5E1) | 1 | **`BCM1_Aussen_Temp_ungef=25.5~26.0℃`(외기온)**, 컴프레서/PTC 상태 |
| `Klima_Sensor_04` (0x5E9) | 1 | `DS_Kaeltemittel_P=32.96`(냉매압), `AAU_Geblaese` |

외기온도는 텔레메트리에 반영 완료(`wayon_vehicle_telemetry.py`).

### 쓰기(제어): 아직 불가 — 3가지 벽
1. **판다 TX 화이트리스트**: MEB 허용 목록에 공조 주소 없음
   (`safety_volkswagen_meb.h`, 진단은 레이더용 `0x700`만 허용)
2. **DBC의 공조 메시지 4종은 전부 상태 보고** (송신자 Gateway).
   HMI/패널 → 공조 ECU 방향의 **명령 메시지는 DBC에 없음**
3. **송신자 충돌**: 조향처럼 릴레이로 순정 ECU를 끊을 수 없어,
   같은 ID를 끼워 넣으면 진짜 ECU와 충돌 → 고장코드 위험

### 진단(UDS) 경로 — 미검증 (2026-08-03 정정)
앞서 "0x746 무응답"이라고 적었으나 이는 **근거 없는 서술이었다.** 실제 주행 로그
(00000039 seg0~2)를 확인하니 콤마 버스에 **진단 트래픽(0x700~0x7FF) 자체가 0건**이다.
즉 공조 ECU가 응답하지 않는다는 증거도, 응답한다는 증거도 없다.

확인하려면 차량이 깨어 있을 때 elm327 모드로 직접 질의해야 한다
(`vw_meb_radar_did_scan.py`가 0x757에 쓰는 방식과 동일).

## 2차 조사 (실차 로깅 필요) — 절차

명령 메시지는 **조작하는 순간에만** 나타나므로 상시 로그로는 안 보인다.
아래를 수행한 뒤 `climate_diff.py`로 변화점을 찾는다.

### 촬영 절차
차 시동을 켜고(주행 불필요) openpilot이 rlog를 기록하는 상태에서,
**각 동작 사이에 10초씩 쉬면서** 순서대로 조작한다. 순서를 지키는 게 중요하다.

```
① 10초 대기 (아무 조작 없음 - 기준선)
② 에어컨 OFF        ③ 10초 대기
④ 에어컨 ON         ⑤ 10초 대기
⑥ 송풍 최대         ⑦ 10초 대기
⑧ 송풍 최소         ⑨ 10초 대기
⑩ 운전석 시트히터 ON ⑪ 10초 대기
⑫ 시트히터 OFF      ⑬ 10초 대기
```

### 분석
```bash
# 기기에서
python3 /data/climate_diff.py <route> <seg> --buses 0,1,2 --max-changes 25
```
10초 간격의 변화 시각과 일치하는 바이트가 명령/상태 후보다.

### 판정 기준
- 후보가 **bus 0 또는 2**에 있으면 → 콤마가 송신 가능한 버스 (희망적)
- **bus 1에만** 있으면 → 콤마는 읽기만 가능, 제어하려면 별도 장치 필요
- 미식별 주소(예: bus1 `0x5E7`)에서 나오면 새 메시지 해독 필요

## 미식별 주소 (명령 메시지 후보)

| 버스 | 주소 | 길이 | 주기 | 비고 |
|---|---|---|---|---|
| 1 | `0x5E7` (1511) | 8 | 5Hz | **Klima_Sensor_02(0x5E1)/04(0x5E9) 사이 — 최유력** |
| 1 | `0x5BE` (1470) | 8 | 2Hz | 저주기 = HMI 명령 특성 |
| 1 | `0x64A` (1610) | 4 | 2Hz | |
| 1 | `0x272` (626) | 8 | 10Hz | |
| 1 | `0x421` (1057) | 8 | 10Hz | |
| 0 | `0x582` (1410) | 4 | 5Hz | bus0라 송신 가능 — 확인 가치 |
| 0 | `0x20D` (525) | 16 | 1Hz | |

## 2차 조사 결과 — 실차 조작 로깅 완료 (2026-08-02, route 00000039--d9057a2808)

절차대로 조작한 흔적이 로그에 그대로 잡혔다.

| 위치 | 조작 | 신호 변화 |
|---|---|---|
| seg23 @52.6s | 에어컨 OFF | `Klima_11.KL_AC_Schalter` 1→0 (bus1) |
| seg24 @8.1s | 에어컨 ON | `KL_AC_Schalter` 0→1 |
| seg24 @35.9~36.7s | 송풍 최대 | `Klima_12.KL_Geblspng_Soll` 5.1V→12.5V (bus0) |
| seg24 @53.9~54.5s | 송풍 최소 | 12.5V→3.3V |
| seg25 @32.0s | 시트히터 ON | `Klima_12.KL_SIH_Soll_li` 0→6단 (bus0) |
| seg25 @48.1~49.3s | 시트히터 OFF | 6→4→2→0단 |

### 판정: 명령 메시지는 콤마 버스에 없다 (제어 불가 확정)

조작 순간(±1초)에 변한 메시지를 전수 조사한 결과, 바뀐 것은 **공조 ECU의 상태
브로드캐스트 2종뿐**이었다.
- `Klima_12`(0x668, bus0) byte1 — 시트히터 단수
- `Klima_11`(0x3B5, bus1) byte4 — 에어컨 상태

HMI(터치 슬라이더/화면) → 공조 ECU 방향의 **명령 메시지는 어느 버스에도 나타나지
않는다.** 즉 공조 조작 트래픽은 콤마가 물리지 않은 컴포트/인포테인먼트 CAN에 있다.

### 그래도 남는 이론적 경로와 그 벽

`Klima_12`는 사실 슬레이브 모듈(시트히터·블로워)에게 주는 **setpoint**라 이걸 위조하면
동작할 여지는 있다. 구조도 유리하다 — **CRC·카운터 없음**, bus0(콤마가 읽는 버스).

그러나 실행 불가 사유:
1. **판다 TX 화이트리스트에 없음** (0x668/0x3B5 모두). 안전코드 수정 필요
2. **송신자 충돌** — 진짜 공조 ECU가 계속 같은 ID를 보낸다. 조향처럼 릴레이로
   순정 송신자를 끊을 수 없어 값이 서로 덮어쓴다
3. 에어컨 컴프레서/히트펌프는 공조 ECU의 제어 루프가 돌려야 해서, setpoint 위조만으로
   예열/예냉이 되지 않는다

**결론: 콤마로 원격 공조는 불가.** 대신 **공조 상태 읽기는 전부 가능**하다
(에어컨 on/off, 송풍 단수, 시트히터 단수, 내기순환, 외기온).
